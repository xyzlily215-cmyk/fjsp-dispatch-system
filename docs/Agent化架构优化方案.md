# 调度系统 Agent 化架构优化方案

> 日期：2026-10-30  
> 范围：将现有 FJSP 调度系统从"能跑的 agent 演示"升级为"架构扎实的 agent 系统"。  
> 现状基线：AGH 底座 + 18 个 fjsp_* 工具 + 四类工具风险标记 + RSI 经验闭环 + MHS 设备唤醒 + MCP Server + agent-bff + 数字孪生页内嵌副驾（详见 `agh-integration/README.md`）。

---

## 1. 现状评估

项目已完成 agent 化的从 0 到 1，核心资产：

| 资产 | 位置 | 状态 |
| --- | --- | --- |
| Agent 运行底座（AGH daemon） | `agh-integration/agnes-harness/` | 可用，绑定较深 |
| 业务工具集（18 个 fjsp_* 工具） | `agh-integration/fjsp-tools/index.mjs` | 已定义入参 schema，缺运行时校验、出参及错误契约 |
| Web 前端桥（HTTP/SSE） | `agh-integration/agent-bff/server.mts` | 可用；前端已有事件类型定义，BFF 无鉴权、无共享契约 |
| 处置方法论 Skill | `agh-integration/skills/fjsp-dispatch/SKILL.md` | 流程与决策混杂 |
| 经验库 + RAG 检索 | `~/.agh/fjsp-experience.jsonl` + `agent-bff/rag.mts` | 可用，无淘汰机制 |
| 设备接入（MHS 虚拟车间） | `agh-integration/mhs-devices/` | 可用，阈值触发式 |
| 审批/幂等/审计 | fjsp-tools + BFF + business-service | 有工具审批和业务审计；BFF 审批身份、重试键复用待补齐 |
| 端到端证据 | `agh-integration/evidence/` | 演示证据为主；验证 driver 自动批准写操作，缺真实审批回归 |

核心结论：**问题不是"要不要 agent 化"，而是把已隐式存在的分层显式化、接口化，并补上度量与闭环。**

## 2. 目标架构：四个职责层 + 横切安全治理

```
┌────────────────────────────────────────────────────────┐
│ 交互层  web-vue 组件 + agent-bff（正式 API 契约）          │
├────────────────────────────────────────────────────────┤
│ 引擎层  引擎抽象接口 ← AGH daemon（实现一）               │
│         + Workflow 编排器（流程骨架）+ 触发器注册表        │
├────────────────────────────────────────────────────────┤
│ 工具层  fjsp-tools（契约校验 + 错误分类 + 影响预览）      │
│         + MCP Server + MHS 设备                          │
├────────────────────────────────────────────────────────┤
│ 记忆层  短期记忆 / 情景记忆（经验库+RAG）/ 语义记忆(Skill) │
└────────────────────────────────────────────────────────┘
   横切治理：身份与授权 + 审批 + taint + 幂等 + 审计
```

安全治理贯穿四层；业务服务是计划、事件和执行状态的权威来源。Workflow 只保存处置进度，不复制业务状态机。

### 2.1 交互层

**现状**：agent-bff 提供会话、审批、数字孪生与检索端点和 SSE 事件流；`web-vue/src/api/agent.ts` 已手写事件类型，页内已有审批卡片。

**优化项**：

- **共享 API 契约**：以同一份 typed schema 约束 BFF 请求/响应与 SSE 事件（user_message / assistant_delta / tool_call / permission_request / turn_end 等），供前后端校验和生成类型；HTTP 端点可据此生成 OpenAPI，SSE 单独定义事件版本。
- **会话快照与断线恢复**：现有 SSE 的 Last-Event-ID 只回放进程内有限缓冲。快照返回会话消息、运行状态、最新事件序号和仍有效的待审批项；快照读取与订阅需衔接，避免两者之间漏事件。BFF 重启后应从 AGH/持久化记录重建可确认状态；无法恢复的审批明确过期并拒绝，不能把旧请求展示为可批准。

### 2.2 引擎层

**现状**：AGH daemon 负责会话和推理；driver（fjsp-agent.mts / fjsp-watch.mts）是验证/值守入口，其中 fjsp-agent.mts 自动批准写工具请求，不是生产工作流运行器。

**优化项**：

- **Workflow 运行器**：先实现一个可恢复的扰动处置实例，再根据实际耦合点抽取 AGH 适配接口；会话、审批和 taint 语义必须纳入接口边界，不能假设四个方法足以无成本替换 runtime。见第 3 节。
- **按需扩展触发器**：MHS 告警先规范化为有来源、设备、时间和去重键的事件，再启动或关联工作流。定时/API 触发有明确用例和重复投递测试后再加入注册表。

### 2.3 工具层

**现状**：18 个工具，无依赖单文件，审批分级 + 幂等键 + 业务错误码透传；MCP Server 与 AGH 插件共用同一实现。

**优化项**（本层是近期工程投入重点）：

- **完善现有 Schema**：复用 `fjsp-tools/index.mjs` 已有入参定义，在 AGH/MCP 执行前做运行时校验；补齐出参、错误 envelope、枚举和契约测试，不再只靠描述文字约束参数。
- **错误分类与恢复动作**：每个错误定义 `retryable / needs-input / needs-human / terminal`、可否重试及重试前置条件。`E_EVENT_IN_PROCESS` 不能自动移动真实事件时间；先核实时间或交给人工处理。`FJSP_INVALID_STATE` 应读取业务现态，不能盲目重试。
- **幂等重试与影响预览**：同一工作流步骤的重试复用相同幂等键，超时或连接中断后先查询业务终态；现有工具每次请求生成新 UUID，需先改造。高风险操作可增加只读影响预览，但预览与执行之间仍须重校验版本。不要将发布写成 `publish ↔ unpublish`：现有回滚会生成新 DRAFT，并重新走评审发布流程。
- **粒度审计**：评估拆分 fjsp_get_dashboard 为更小的只读工具（list_events / get_kpi 等），降低上下文占用。

### 2.4 记忆层

显式分三类，生命周期与更新机制各不相同：

| 类型 | 内容 | 现有实现 | 缺口与优化 |
| --- | --- | --- | --- |
| 短期记忆 | 会话上下文 + 工作流进度 | AGH 会话上下文；业务服务保存事件与方案状态 | **持久化工作流检查点**：记录节点、业务对象 ID 和待办审批；新会话的未消费事件/待评审方案从业务服务查询并注入摘要，避免再造一份会过期的业务状态 |
| 情景记忆 | 处置经验（事件→模式→KPI 结果） | JSONL 仅追加 + e5-small 向量/BM25 双路 RRF 融合 | **先接结果反馈再降权**：以业务结果、人工驳回/返工及时间标记经验质量；保留原始记录，检索时降权或过滤。补充负荷时段、交期紧迫度等情景字段，比较同类场景，避免仅凭历史平均 KPI 推荐模式 |
| 语义记忆 | 处置方法论（判断规则） | fjsp-dispatch SKILL.md | **建蒸馏回路**：高频成功经验定期固化回 Skill 决策树（半自动 + 人工 review），检索降级为兜底，省 token 且更稳 |

**关于向量数据库的结论**：当前先沿用本地检索；记录量、检索延迟、更新一致性或多实例部署触及实测瓶颈时，再评估 SQLite + sqlite-vec 等方案。数据库选型不以未经测量的固定数量阈值决定。

### 2.5 安全层（纵切）

**现状**：工具有 READ/WRITE/HIGH_RISK/DESTRUCTIVE 四类风险标记；AGH 有审批与 taint，业务服务有 JWT、幂等和审计。BFF 目前无鉴权；MCP 的 `_confirm: true` 是调用方参数，不能证明人工批准。

**优化项**：

- **先建立身份与审批边界**：BFF 验证用户身份并将会话绑定到用户；审批请求绑定工具名、参数摘要、业务对象、有效期和可审批角色，批准时重新校验。Origin/loopback 限制不能代替鉴权；MCP 入口需依赖受信任客户端的真实审批能力或独立审批服务，不能把 `_confirm` 当作人工凭证。
- **谨慎配置审批策略**：默认拒绝；可配置项只覆盖允许自动执行的低风险操作。评审、发布和破坏性操作必须继续由具备相应角色的人确认，并由业务服务校验业务状态与权限。
- **审计聚合视图**：关联已认证操作者、审批请求、工具调用、业务请求 ID、幂等键与业务副作用；不能只依赖客户端可填写的来源/会话头证明审批人。支持导出供复核。

## 3. 运行模式：可恢复 Workflow + Agent 决策节点

### 3.1 职责划分

处置流程（基线排程、扰动处置、评审发布）的顺序和业务守卫大多是确定性的，现以自然语言写在 SKILL.md 里。将步骤推进交给代码，策略建议、冲突解释和材料生成交给 Agent；决策节点与生成节点可先共用同一模型，不必为架构名称拆成多个自治 Agent。

> **步骤顺序、状态校验和人工挂起由 workflow 代码约束；Agent 给出经校验的策略建议和解释。**

### 3.2 结构

```
入口：人工请求 / 经确认、去重的 MHS 告警
  ↓
Workflow 运行器（持久化检查点 + 业务状态核对）
  接收事件 → 登记事件 → 检索经验 → [Agent 建议模式/权重]
             → 校验建议 → 重调度 → 轮询结果 → 对比方案
             → [Agent 生成评审材料] → 提交评审 → 挂起待人工决策
  异常分支：状态冲突 / 超时 / 不可行 / 审批拒绝 → 核对业务现态后恢复或终止
  后续流程：人工评审通过并独立确认发布后，才调用发布工具
```

### 3.3 三类角色

| 角色 | 性质 | 职责 | 来源 |
| --- | --- | --- | --- |
| Workflow 运行器 | 确定性代码 | 保存步骤进度、重试与超时分支、审批挂起；每次推进从业务服务读取计划状态并校验 | 新增：将 SKILL.md 的流程部分翻译成可恢复工作流 |
| 决策型 Agent | LLM | 判断节点：建议重调度模式/权重（结合经验检索）、解释 FEASIBLE/conflicts；重试与升级人工由运行器根据策略和业务状态决定 | skill 的决策部分 + RSI 检索 |
| 生成型 Agent | LLM | 产出人类消费品：处置报告、评审材料（扰动率/KPI 差值/风险提示） | skill 末尾的报告职责独立出来 |

### 3.4 收益

1. **可测试**：workflow 骨架用确定性测试覆盖（mock 工具断言流程走向）；agent 节点用 golden 场景单独评估。
2. **审批语义明确**：评审/发布成为 workflow 一等公民的挂起节点，不再靠"停下请人工确认"约束模型自觉。
3. **控制模型调用**：仅在策略判断与材料生成等节点调用 LLM；是否降低 token 用量和失败率，按第 4 节与现有流程对照测量。
4. **SKILL.md 瘦身**：只留"怎么判断"（方法论），"按什么顺序做"交给代码。

### 3.5 工作流实例与恢复协议

- **最小检查点**：`workflowId`、触发源与去重键、`eventId/taskId/planVersionId`、当前节点、尝试次数、该步骤幂等键、待审批请求与截止时间。先保证单实例可恢复；需要多实例时再增加租约或并发控制。
- **恢复顺序**：重启后先查询业务服务中的事件、任务和计划现态，再判断步骤是否已产生副作用。网络结果未知时复用原幂等键并核对终态；审批请求无法确认仍有效时设为过期，重新发起，不回放旧批准。
- **分支与人工边界**：INFEASIBLE 可在解释冲突后按预设策略尝试 FULL_RESCHEDULE；`E_EVENT_IN_PROCESS` 需要核实时间，不能自动改变事件事实。审批拒绝、评审驳回、乐观锁冲突均有显式停止或重新读取分支，重试设次数上限。
- **Agent 节点契约**：策略节点输入 = 事件 + 经验检索结果 + 当前约束，输出 = `{mode, weights, rationale}`；校验枚举、数值范围及权重规则后才执行。生成节点只引用工具返回的 KPI，不承担写操作决策。

### 3.6 落地路径（在 AGH 上）

- **轻量路线（先走）**：新增独立的工作流运行器和检查点存储，复用现有 fjsp-tools 与 AGH 会话；`fjsp-agent.mts` 保留为验证入口，不把自动批准逻辑带进运行器。先实现扰动处置一条流程和人工挂起/恢复。
- **扩展路线（按需）**：基线排程、评审发布通过同一运行器扩展。只有在现有运行器出现明确的并发、定时或运维瓶颈后，才评估通用工作流引擎；AGH 适配接口依据已验证的调用与审批语义抽取。

## 4. 度量与评估体系（贯穿所有优化的地基）

没有度量，其他优化都是盲改；且"agent 在 N 个标准场景下成功率 X%"是论文与答辩的直接论据。

- **Golden 评估集**：固定数据快照与算法 seed，覆盖设备故障、紧急插单、混合扰动、不可行解、重复告警和审批拒绝。分别度量业务成功率、误操作数、人工介入率、步骤数、耗时与 token 用量；与当前 Skill 驱动方案在同一场景下对比。
- **分层回归**：确定性工作流用模拟工具验证分支；业务集成测试验证真实状态和副作用；模型场景单独评估决策质量。现有 `fjsp-agent.mts` 会自动批准写操作，只能作为标注了“模拟审批”的验证入口，不能证明人工审批正确。CI 使用隔离数据库和独立凭据，不触碰演示环境。
- **关键断言**：发布成功须满足 FEASIBLE、无硬约束冲突、完成对比、评审通过且审批人有权限；审批拒绝后无发布，重复投递不产生第二次写入，超时/重启后可恢复，乐观锁冲突后重新读取。
- **结构化指标与失败归档**：按 workflowId 记录节点耗时、工具与模型调用、审批状态、业务终态和错误类别；归档失败或人工驳回场景用于复盘。审批通过率只作流程指标，不单独当作决策质量指标。

## 5. 实施路线图

| 阶段 | 内容 | 验收重点 |
| --- | --- | --- |
| P0 | BFF 身份与会话归属、审批身份绑定；固定场景评估集与隔离回归环境 | 越权审批被拒；拒绝审批无副作用；基线指标可复现 |
| P1 | 现有工具契约校验、错误分类、步骤幂等键复用；BFF 共享 API/SSE 契约 | 非法参数被挡在执行前；未知结果可安全核对与重试；前后端契约测试通过 |
| P2 | 独立的扰动处置工作流运行器、检查点、人工挂起与恢复 | 重启、超时、重复告警、乐观锁冲突均到达预期终态且不重复写入 |
| P3 | 会话快照与审计聚合；从业务服务查询待办事项 | 页面刷新可恢复有效审批，过期请求不可批准；审计链可按 workflowId 复核 |
| P4 | 经验结果反馈、检索降权与情景字段；基线排程/评审流程扩展 | 相同评估集上报告成功率、误操作、人工介入和成本的变化 |
| P5 | AGH 适配接口、通用触发器、引擎/向量库选型（按需） | 有明确耦合或负载证据，再投入相应抽象或基础设施 |

每阶段保留可复现的测试场景、指标与 `evidence/` 证据；架构类改动同步更新架构图。指标劣化时记录原因和取舍，不用“脚本全绿”替代效果评估。

## 6. 风险与前提

- **AGH 绑定风险**：agnes-harness 未随仓库分发、CLI 有已知稳定性坑。先固定版本、保存复现步骤与契约测试；运行器稳定后按实际耦合点抽取适配接口。
- **审批绕过风险**：MCP `_confirm` 和测试 driver 的自动批准均不代表真实人工确认；生产路径必须有认证身份、角色校验、请求绑定与拒绝分支。
- **状态分裂风险**：业务计划、事件与任务状态以业务服务为准；工作流检查点只保存流程进度，重启后必须核对业务现态。
- **Workflow 过度设计风险**：先跑通一条扰动处置流程的挂起与恢复，再扩展另外两条流程；不预设必须接入重量级引擎。
- **经验库冷启动与偏差**：先记录评审/返工反馈；样本不足或场景不可比时退回明确的默认策略，不能把历史平均 KPI 当成因果最优解。
