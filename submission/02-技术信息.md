# 02 技术信息

## 1. AGH 的作用

本作品以 **AGH（Agnes Harness）** 为智能体运行底座：

- 所有大模型调用只经由 Agnes 模型，AGH 负责任务编排、工具调度、审批拦截与会话账本记录；
- AGH 源码副本位于 `agh-integration/agnes-harness/`（上游 `github.com/AgnesAI-Labs/agnes-harness`，Apache-2.0，要求 Node ≥ 24.10，入口 `packages/cli/dist/local/agnes.mjs`，`serve` 子命令在 4177 端口启动工作台）；
- 自研 AGH 工具插件 `agh-integration/fjsp-tools/`（包名 `@fjsp/fjsp-tools`，单文件 `index.mjs`）把业务系统能力封装为 16 个 `fjsp_*` 工具供模型调用（含 RSI 经验库查询/沉淀工具）；
- 方法论 Skill `agh-integration/skills/fjsp-dispatch/SKILL.md` 约束智能体行为：基线流程、扰动处置流程、处置经验闭环、错误码处理；处置操作只准使用 `fjsp_*` 业务工具，设备感知使用 MHS 设备工具（`read_device` / `watch_device` 等），两者分工与纪律边界在 Skill 中写明；
- MHS 设备接入：AgnesHub（`http://127.0.0.1:4180`，Devices 面板）经 MHS 插件接入虚拟车间 `agh-integration/mhs-devices/machine-m03.py`——可一次拉起与业务清单对齐的 8 台虚拟机床（cnc-m01~m08），每台上报温度/振动/转速（2Hz）与实时渲染的「状态面板画面」（image 数据源，状态灯 + 温度曲线，对应官方火星基地案例的相机画面），全部机床声明 placement 落在共享的 workshop 车间地图上（对应官方案例的世界地图）；故障演示机 cnc-m03 对应业务机台 M-03（`kill -USR1` 注入过热故障、`kill -USR2` 恢复），设备异常自动上报并唤醒会话；值守驱动 `agh-integration/driver/fjsp-watch.mts` 附着已有会话等待 `watch_device` 唤醒并程序化审批；
- 端到端验证驱动 `agh-integration/driver/fjsp-agent.mts` 通过 AGH Node SDK 直连 daemon，发中文指令、程序化批准写工具审批、账本事件落盘 jsonl，形成可复核的执行证据；`scripts/render-trace.mjs` 可把事件流渲染为单文件 HTML 时间线（工具调用/审批/结果逐条可见，对应官方案例「过程可观察、可检查」的要求）。

### 与官方案例的对标（分层决策架构）

参照官方火星基地与王者荣耀案例的组合方式，本作品把调度决策拆为三层：

| 层 | 承担者 | 职责 |
|----|--------|------|
| 理解与分析层 | `agnes-3.0-flash` 大模型 | 自然语言指令理解、处置流程编排、方案 KPI 解读与中文报告 |
| 决策层 | Skill 方法论 + RSI 经验库（`fjsp_experience_query`） | 重调度模式/权重等高频策略选择：优先采用历史同类事件的最优参数组合，而非每次默认试错 |
| 执行层 | `algorithm-service` 求解内核 + 业务系统状态机 + 四级审批 | 把决策落实为真实的排程计算与受控的业务写入（幂等、乐观锁、审计落库） |

执行反馈回流：每次处置结束经 `fjsp_experience_record` 沉淀「事件类型 → 模式/权重 → KPI 结果」，形成「策略与环境交互 → 产生经验 → 改进后续策略」的 RSI 闭环（端到端证据见 `agh-integration/evidence/agh-rsi-*.jsonl`：第二次同类故障直接命中推荐模式，跳过第一次的局部重排试错）。

### 模型参与的核心环节

1. **基线排程决策**：接收「完成基线排程并发布」等自然语言指令，自主编排看板查询 → 创建基线 → 轮询任务状态 → 发布的完整链路；
2. **扰动处置**：针对设备故障 / 紧急插单事件，先查处置经验库（`fjsp_experience_query`）获取同类事件的历史最优策略，再执行局部或完全重调度并解释依据；
3. **方案对比解释**：读取多方案 KPI，输出中文对比报告与处置结论（如「故障落在空闲窗口、零扰动、无需发布」），并能主动发现未消费事件、未发布方案等异常状态；
4. **发布前环境一致性复核**：MHS 告警触发的扰动在发布前用 `read_device` 确认设备真实状态与计划假设一致，计划与环境状态保持同步（对应官方案例「计划和环境状态需要保持一致」）；
5. **审批流人机协同**：写操作触发审批时主动停下请人工确认，按「提交评审 → 人工审批 → 发布」三段式推进高风险操作。

## 5. 专业软件 / 仿真环境

- **AGH（Agnes Harness）**：智能体运行底座，4177 端口工作台，承担模型调用、工具编排、审批与账本；
- **PostgreSQL 16**（Docker Compose 单容器）：业务持久化与审计存储；
- **调度仿真环境**：`algorithm-service` 即仿真内核，对 FJSP 实例求解并输出甘特/KPI；扰动事件（故障、插单）驱动重调度仿真；
- 辅助工具：`scripts/perf-baseline.sh`（7 条核心 SQL 的 EXPLAIN ANALYZE 性能基线）、`scripts/collect-evidence.sh`。

## 6. API / 设备接口

### 6.1 AGH 工具接口（`fjsp_*` 16 个，HTTP 调业务服务）

工具调用携带 JWT 登录令牌、`Idempotency-Key` 幂等键、审计头 `X-Source: agh`。审批策略四级：

| 级别 | 含义 | 工具 |
|------|------|------|
| READ | 只读，免审批 | `fjsp_get_dashboard`（看板）、`fjsp_task_status`（任务状态轮询）、`fjsp_compare_plans`（方案对比）、`fjsp_experience_query`（处置经验查询）等 |
| WRITE | 写操作，需审批 | `fjsp_create_baseline`（基线排程）、`fjsp_report_breakdown`（故障上报）、`fjsp_insert_order`（紧急插单）、`fjsp_reschedule`（重调度）、`fjsp_submit_review`（提交评审）、`fjsp_experience_record`（处置经验沉淀）等 |
| HIGH_RISK | 高风险，需审批 | `fjsp_approve_review`（审批通过）、`fjsp_publish`（方案发布） |
| DESTRUCTIVE | 破坏性，需审批 | `fjsp_reset_demo`（演示数据重置） |

> 各级别内工具的完整清单见 `agh-integration/fjsp-tools/index.mjs`；发布路径固定为「提交评审 → 停下请人工 → 审批 → 发布」三段式人工确认。处置经验库存于 `~/.agh/fjsp-experience.jsonl`（仅追加 JSONL，可用 `FJSP_EXPERIENCE_FILE` 覆盖）。

### 6.2 业务 REST API

- 业务服务入口：`http://localhost:8081/api/v1`（默认前端入口 `http://127.0.0.1:8082/index.html?api=http://localhost:8081/api/v1`）；
- 认证：Spring Security + JWT；
- 横切机制：`Idempotency-Key` 幂等、乐观锁（并发发布返回 `E_VERSION_STALE`）、审计（`X-Source` / `X-AGH-Session-Id` 透传并落库）、SSE 事件推送；
- 错误码体系：见《研发附录》V1.1 API 契约与错误码章节（如 `E_DUPLICATE`、`E_VALIDATION`、`E_VERSION_STALE`）。

### 6.3 设备接口

本作品面向单车间管理层级，设备现经 MHS / AgnesHub（`http://127.0.0.1:4180`，Devices 面板）接入：虚拟车间（`agh-integration/mhs-devices/machine-m03.py`）与业务设备清单 M-01~M-08 对齐，每台机床提供温度/振动/转速 2Hz 数据源与状态面板画面（image 源，1Hz JPEG），并以 placement 落在共享 workshop 车间地图上，Devices 面板呈现完整车间布局；故障演示机 cnc-m03（对应业务机台 M-03）演示「设备异常自动上报 → 唤醒 Agent → 故障处置」链路；MHS 感知工具（`read_device` / `watch_device` 等）免审批，`fjsp_*` 业务写操作仍走四级审批。未接入 PLC/OPC-UA 等工业协议。
